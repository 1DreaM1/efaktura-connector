Prehľad API

Čítanie ≈ 23 min7 sekciíUpravené 27. 11. 2026

Toto je prehľad endpointov zabudovaných v balíku podľa DataHosting SAPI-SK OpenAPI, Peppol Gateway v1 OpenAPI a Integrator API OpenAPI. Tento balík cieli na DataHosting API; verejný, poskytovateľsky nezávislý SAPI-SK kontrakt nie je jeho implementačným cieľom.

Integrator API používa samostatný klient a integrátorský token.

docs/eFaktura/api/openapi.json je lokálny kombinovaný snapshot všetkých troch skupín. V snapshot-e sú SAPI cesty pod /sapi a Gateway aj Integrator API cesty pod /v1; transport pripája každú cestu ku nakonfigurovanému base_url.

SAPI a Gateway používajú SAPI Bearer token, kým Integrator API používa X-Integrator-Token.

Hodnotu base_url profilu klienta nastavte na serverovú adresu servers z OpenAPI, napríklad https://test-sapisk.datahosting.sk. Implementácia odstráni koncové lomky, ale zachová cestovú časť URL a pripojí ju pred cestu každého endpointu.

Pri štandardnom nasadení preto použite serverový koreň bez /sapi: SAPI endpointy už obsahujú celú cestu /sapi/... a Gateway endpointy /v1/....

Ak API stojí za reverznou proxy so spoločným prefixom, ten možno uviesť v base_url (napríklad https://api.example.sk/proxy); výsledné cesty budú /proxy/sapi/... a /proxy/v1/....

Prefix /sapi alebo /v1 nepoužívajte ako spoločný, pretože by sa pripojil aj k druhej skupine endpointov.

Testovacie OpenAPI uvádzajú server https://test-sapisk.datahosting.sk. Nastavte base_url na server príslušného prostredia.

Tok jedného API volania¶[upraviť zdroj]

Nasledujúci diagram zobrazuje tok SAPI a Peppol Gateway volaní od Core kontraktu po typovaný výsledok. Gateway používa token získaný zo SAPI.

Integrator API má samostatný klient a transport s hlavičkou X-Integrator-Token; jeho endpointy a mapovanie sú uvedené v samostatnej časti nižšie.

Ak endpoint potrebuje telo odpovede, ApiConnector dekóduje JSON alebo bezpečne parsuje XML a odovzdá údaje statickej factory (mapperu) endpointu, ktorá z nich vytvorí Core model. Operácia send() kontroluje iba HTTP úspech a telo nedekóduje.

Neúspešný HTTP status skončí ako ProviderErrorResponseException; chybný formát alebo štruktúra úspešnej odpovede ako InvalidProviderResponseException. Endpoint vracia Core model (alebo bool/void) a adaptér ho odovzdá hostiteľovi.

Samotné vrstvy, retry a správanie pri 401 rozoberá HTTP transport a autentifikácia; mapovanie konkrétnych endpointov pokračuje v tabuľkách tejto stránky.

SapiTokenProvider získava a cacheuje access token cez DataHosting /sapi/auth/token. Po expirácii alebo zneplatnení cache získa nový token cez client credentials.

forget(SapiToken) maže iba lokálny zamietnutý token (čerstvý token iného workera nechá); DataHosting kontrakt použitý týmto balíkom neobsahuje vzdialené operácie na obnovu ani zrušenie tokenu.

Pri čítaní odpovedí sa neznáme neprázdne statusy, webhook udalosti, režimy Integrator API a hodnoty payloadFormat zachovajú v modeloch. Statusové value objecty ponúkajú isKnown(); WebhookEventType používa isSupported().

Hostiteľ má podľa výsledku rozhodnúť, ako novú hodnotu spracovať. Pri odoslaní SAPI iba známy status ACCEPTED vyžaduje receivedAt. Hodnota OAuth token_type sa porovnáva bez ohľadu na veľkosť písmen a normalizuje sa na Bearer.

Požiadavky, odpovede a HTTP statusy SAPI¶

Všetky SAPI operácie okrem POST /sapi/auth/token vyžadujú Bearer token. Odoslanie, príjem a acknowledge vyžadujú aj participant hlavičku podľa tabuľky; token status ju nevyžaduje. Hviezdička označuje povinné pole podľa OpenAPI.

Všetky deklarované chybové statusy vracajú SapiErrorResponseEnvelope s povinným poľom error; jeho SapiError vyžaduje category, code, message, retryable a correlation_id, kým details sú voliteľné.

OpenAPI používa pri odpovediach podľa operácie */* alebo application/json.

Integrator API¶[upraviť zdroj]

IntegratorAccountClientFactory vytvára samostatný IntegratorAccountClientInterface klient z IntegratorAccountConfiguration. Bežné operácie používajú X-Integrator-Token; odoslanie PDS subjects používa podpis X-PDS-Secret namiesto API tokenu.

OAuth poverenia spravovaných klientov sa používajú pri ich neskorších SAPI/Gateway volaniach.

Odpovede sa mapujú na typované Core modely v Core\IntegratorApi; neúspešné statusy končia ako ProviderErrorResponseException.

Všetky úspešné polia sú podľa OpenAPI voliteľné a mapper zachováva chýbajúce hodnoty ako null (zoznamy stránok sa pri vynechanom poli vrátia ako prázdne). Pri PDS požiadavke sa JSON telo vytvorí z PdsSubjectBatch a podpis sa vypočíta nad presnými bajtmi odosielaného tela.

PDS endpoint používa samostatný ApiConnector a PdsAuthenticatedRequestSender nad spoločným transportom. Sender vyžaduje jeden neprázdny podpis X-PDS-Secret a odstraňuje hlavičky Authorization a X-Integrator-Token.

Použitie, konfigurácia a retry hranice sú v návode Integrator API.

Integrátor ID a OAuth client ID v Integrator API sú hodnotové typy IntegratorId a OAuthClientId. Participant ID používa zdieľaný typ Domain\EFaktura\Participant, rovnako ako SAPI a Gateway.

Stav OAuth klienta a režim kontraktu vracajú typy IntegratorClientStatus a ParticipantContractMode; neznáme neprázdne hodnoty z odpovede sa zachovajú a hostiteľ ich klasifikuje cez isKnown().

Vstupné DTO naďalej prijímajú príslušné typy a konfiguráciu overujú podľa podporovaných hodnôt.

Telo požiadaviek a mapovanie odpovedí¶[upraviť zdroj]

Endpointové triedy používajú názov <Akcia><Zdroj>Endpoint, napríklad SendDocumentEndpoint alebo ListWebhooksEndpoint.

Keď operácia potrebuje viac vstupných hodnôt, endpoint prijíma typovaný Core request, napríklad SendDocumentRequest; pri jednoduchších operáciách prijíma priamo typovaný kontext alebo identifikátor.

Endpoint zostaví ApiRequest a výsledok vráti ako Core model (alebo bool/void), ktorý vytvorí statická <Resource>Factory alebo <Resource>Mapper v Api/Response/; samostatné response DTO ostáva iba pre OAuth SapiTokenResponse.

Provider polia a ich serializácia zostávajú na hranici Infrastructure.

Peppol documentTypeId a processId v Core a Domain modeloch reprezentujú hodnotové objekty PeppolDocumentTypeIdentifier a PeppolProcessIdentifier.

Provider JSON telá zachovávajú reťazcový tvar OpenAPI; request mappery a response factory hodnoty prevádzajú medzi týmito hranicami.

Retry a backpressure¶[upraviť zdroj]

DefaultHttpRequestExecutorFactory skladá cURL, retry, circuit breaker a backpressure. RetryPolicy::default() povoľuje tri pokusy celkovo; exponenciálne oneskorenie začína na 500 ms a má strop 30 sekúnd.

ApiRequest povoľuje retry pre GET predvolene; ostatné metódy sa opakujú iba vtedy, keď ich endpoint výslovne označí ako bezpečné.

Bezpečné požiadavky opakujú chyby spojenia a odpovede 5xx/429; provider odpovede sa opakujú len vtedy, keď rozpoznaná chybová obálka obsahuje retryable: true.

Integrator klient vytvára a aktivuje OAuth klientov s idempotency key a retry-safe označuje aj úplnú náhradu participant prístupov cez PUT. Rotáciu secretu a odstránenie klienta automaticky neopakuje.

Pri samostatnom skladaní sa vlastná politika nastaví cez HttpRequestExecutorOptions::defaults()->withRetryPolicy(...) a odovzdá do DefaultHttpRequestExecutorFactory::create().

Zámok sa nastavuje cez withExecutionLock(); predvolený FileHttpRequestExecutionLock používa aktuálny pracovný adresár ako koreň aplikácie. Pri načítaní runtime konfigurácie použite createFromRuntimeConfiguration().

Laravel bridge nastavuje retry cez runtime.retry; premenné prostredia pre tieto hodnoty sú uvedené v Laravel konfigurácii.

Predvolená politika čaká synchronne najviac jednu sekundu na jeden retry po provider odpovedi. Pri dlhšom platnom Retry-After vráti executor odpoveď bez ďalšieho čakania.

Metóda retryAt() na provider výnimke sprístupní hodnotový objekt RetryDeadline; na plánovanie v hostiteľskej aplikácii použite jeho unixTimestamp().

Ak retry vrstva vráti konečnú HTTP 429 odpoveď, tá zostáva ProviderErrorResponseException a backpressure uloží cooldown z Retry-After, prípadne jednu sekundu, ak hlavička chýba alebo je neplatná.

Ďalšie volania v rovnakom transportnom scope sa pred uplynutím cooldownu neodošlú. SAPI/Gateway scope sa viaže na origin, OAuth klienta a scope a nemení sa pri obnove Bearer tokenu; Integrator scope používa origin a hash ID integratora a nemení sa pri rotácii tokenu.

Počas cooldownu volania vyvolajú RequestDeferredException s hodnotou RetryDeadline v retryAt(). Táto výnimka znamená, že daná požiadavka neodišla do siete.

Samostatná skladba používa in-memory stav pre backpressure a circuit breaker. Laravel bridge ich zdieľa cez Laravel Cache a pre zápisy používa cache locky, ak ich Laravel a store podporujú; inak koordinuje lock operácie lokálnymi súborovými zámkami.

Tie fungujú len medzi procesmi na tom istom hostiteľovi. Circuit breaker otvorí obvod po piatich neúspešných požiadavkách (chyba spojenia alebo odpoveď 5xx) v priebehu 60 sekúnd na 30 sekúnd a po prestávke povolí jeden skúšobný request.

HTTP 429 nie je zlyhanie circuit breakera.

Keď je execution lock zapnutý, BackpressureHttpRequestExecutor ho drží počas kontroly cooldownu a vykonania jedného pokusu; pred čakaním retry vrstvy ho uvoľní. Cooldown po 429 zapisuje RateLimitRecordingHttpRequestExecutor pod retry vrstvou.

Samostatná Core skladba predvolene používa FileHttpRequestExecutionLock, ktorý je oddelený podľa kanonickej cesty aplikácie a OS používateľa a koordinuje iba procesy na rovnakom hostiteľovi; aktuálny pracovný adresár je predvolený koreň aplikácie.

Laravel bridge používa Cache::lock() zo zvoleného cache store, ak je lock API dostupné; pri Laravel 5.6 alebo cache store bez tohto API použije lokálny súborový lock. Zdieľaný store s podporou atómových zámkov môže koordinovať celý request aj medzi hostmi.

Pri laravel.request_execution.execution_lock.driver=file sa použije súborový lock s koreňom basePath(), ktorý sa medzi hostmi nezdieľa.
