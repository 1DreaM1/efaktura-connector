Tok dát a prehľad tried

Čítanie ≈ 17 min6 sekciíUpravené 27. 11. 2026

Táto stránka sleduje údaje od verejného kontraktu konektora po API odpoveď alebo výsledný UBL model. Opisuje implementáciu balíka; poradie kontrol, uloženie dokladov a obchodný workflow určuje hostiteľská aplikácia.

Zostavenie služieb¶[upraviť zdroj]

Hostiteľ používa kontrakty z Core a môže ich napojiť na predvolené implementácie v Infrastructure. Laravel service provider skladá predvolené služby do kontajnera. Pri samostatnom použití bez Laravelu vytvorí tieto objekty hostiteľ.

SapiClientRegistry vracia klienta podľa aliasu alebo predvoleného nastavenia a vytvára ho až pri prvom použití. SapiClientFactory pre daný profil skladá autentifikovaný ApiConnector a SapiClient; každý klient má vlastný SapiTokenProvider.

Executor môže byť zdieľaný alebo vytvorený pre konkrétny profil podľa konfigurácie factory. SapiClient vytvára jednotlivé adaptéry až pri prvom vyžiadaní príslušnej služby a potom ich uchováva v typovaných vlastnostiach.

UblDraftSubmission zdieľa SAPI submission gateway a kontrola schopnosti príjemcu zdieľa discovery provider. SapiClient preto drží služby bez reťazcovej mapy cache; verejné Core kontrakty klienta sa nemenia.

Core definuje verejné porty, vstupné a výstupné dátové objekty a technické výnimky. Domain normalizuje hodnoty, napríklad identifikátor participanta, stav dokladu či UBL údaje. Infrastructure vytvára API požiadavky, vykonáva HTTP a mapuje odpovede na typované modely.

IntegratorAccountClientFactory skladá jeden ProviderTransport (forIntegratorAccount()) a dva ApiConnector objekty.

Bežné operácie idú cez IntegratorTokenRequestSender, ktorý nastaví X-Integrator-Token; PDS endpoint používa PdsAuthenticatedRequestSender nad tým istým transportom. PDS sender vyžaduje práve jeden neprázdny X-PDS-Secret a odstráni hlavičky Authorization aj X-Integrator-Token.

Obe vetvy obchádzajú AuthenticatedRequestSender a SapiTokenProvider. Oba konektory dostane IntegratorAccountClient, ktorý z nich vytvorí typované skupiny pre správu klientov, účastníkov, súhrny dokladov a PDS a deleguje do nich operácie.

Toto rozdelenie je interné pre Infrastructure; verejné operácie naďalej poskytuje jedno IntegratorAccountClientInterface. Integrator OAuth klienti sa preto dajú spravovať bez toho, aby integrátorský token vstupoval do konfigurácie bežného SAPI OAuth klienta.

SAPI OAuth token sa získava cez štandardné SAPI a používa sa aj pre volania Peppol Gateway.

SapiTokenProvider najprv kontroluje token v pamäti, potom cache; ak je nakonfigurovaný SapiTokenRefreshLockInterface, po získaní zámku znovu načíta cache, aby obmedzil duplicitné obnovy.

Laravel bridge poskytuje cache lock, ak je dostupný, inak lokálny súborový zámok; samostatné použitie môže zámok dodať hostiteľ.

Identita participanta nie je súčasťou OAuth konfigurácie ani token cache kľúča; endpoint ju pre účastnícke volanie pridá cez ApiRequest::forParticipant() do hlavičky X-Peppol-Participant-Id.

Integrator API má oddelený IntegratorAccountClient, ktorý neposiela SAPI Bearer token; ProviderTransport::forIntegratorAccount() viaže jeho nastavenia na base URL a pripraví scope key pre zdieľanie cooldownu.

Bežné Integrator volania prechádzajú cez tokenový sender. PDS endpoint používa samostatný ApiConnector a PdsAuthenticatedRequestSender nad tým istým transportom; sender overí podpisovú hlavičku a odstráni ostatné autentifikačné hlavičky.

ApiConnector kontroluje úspešný HTTP status a dekóduje JSON alebo bezpečne parsuje XML. Neúspešný status sa zmení na ProviderErrorResponseException, ktorá zachová status, hlavičky a telo a dostane rozpoznaný ProviderErrorEnvelope z ProviderErrorEnvelopeParser.

Neplatný JSON/XML alebo chýbajúce povinné polia úspešnej odpovede vyvolajú InvalidProviderResponseException s HTTP kontextom.

Predvolený executor vytvára DefaultHttpRequestExecutorFactory: cURL, voliteľné logovanie a metriky, retry podľa RetryPolicy, circuit breaker a backpressure. Vykonanie prechádza zvonka dovnútra cez circuit breaker, retry, backpressure, logger, metriky a cURL.

Bez frameworku používajú tieto ochrany in-memory stav; Laravel bridge ho ukladá do Laravel Cache a koordinuje lock operácie cache alebo lokálnymi súborovými zámkami. GET je štandardne bezpečný na retry.

Iné metódy sa opakujú iba pri výslovnom označení endpointom. Pri HTTP 401 AuthenticatedRequestSender zahodí lokálny token a zopakuje volanie s novým tokenom najviac raz. Toto autorizačné opakovanie je samostatné od HTTP retry.

Napríklad SendDocumentEndpoint posiela idempotency key, ale nastaví retrySafe(false), takže nejednoznačný výsledok odoslania sa automaticky neopakuje pri chybe spojenia ani retryable odpovedi.

  1. Vstup a mapovanie. Hostiteľ podľa potreby získa pomenovaný alebo predvolený SapiClient cez SapiClientRegistry a zavolá Core kontrakt poskytnutý klientom s typovanými hodnotami. Adaptér odovzdá typovaný request alebo kontext endpointu, ktorý vráti Core model. Endpoint prevedie vstupné hodnoty na provider hlavičky, query a telo a zostaví ApiRequest.
  2. Príprava ApiRequest. Cesta zostáva relatívna k poskytovateľovi. Názvy path parametrov musia presne zodpovedať placeholderom v šablóne; hodnoty sú neprázdne reťazce (biele znaky samy nestačia) alebo celé čísla, hodnoty . a .. sa odmietnu a ostatné sa kódujú cez rawurlencode() ako jednotlivé segmenty.
    Query hodnoty môžu byť reťazce, celé čísla alebo null; null sa vynechá, 0 a prázdny reťazec sa zachovajú a iné typy vyvolajú InvalidInputException. Pri opakovanom withQuery() neskoršia nenull hodnota nahradí skoršiu hodnotu s rovnakým kľúčom; null ju nevymaže.
    Výsledok sa serializuje vo formáte RFC 3986. withJsonBody() zakóduje telo hneď pri zostavení requestu; neplatné JSON dáta preto zlyhajú ešte pred získaním tokenu alebo sieťovým volaním. Predvolená hlavička Accept žiada JSON; endpoint môže zvoliť XML.
    ApiRequest::forParticipant() pridá SAPI/Gateway participant ID do hlavičky a skontroluje, že jeho schéma je aktívna a registrovateľná. Pri novom dokumente OutboundDocumentPayload používa rovnakú kontrolu. Integrator requesty namiesto Participant používajú neprázdne participant ID reťazce a schému číselníka lokálne nekontrolujú.
    DocumentRequestContext ostáva iba metadátom pre logovanie a neposiela sa poskytovateľovi. ApiRequest::httpMethod() a HttpExchangeRequest::httpMethod() vracajú typovaný HttpMethod; na HTTP hranici sa jeho názov prevedie cez value(). GET je bezpečný na opakovanie predvolene; ostatné metódy nie.
  3. Prevod na transportný request. ApiRequest a HttpExchangeRequest zdieľajú internú abstraktnú triedu AbstractHttpRequest, ktorá drží ich spoločné HTTP údaje. ApiConnector z nej zostaví HttpExchangeRequest na jednom mieste: prenesie metódu, cestu s query, hlavičky, telo, Accept, kontext pre logy a príznak bezpečného opakovania.
    Base URL a scope sa doplnia neskôr v transportnej vrstve.
  4. Autorizácia a URL. Pri SAPI a Gateway volaní AuthenticatedRequestSender získa token cez SapiTokenProvider a nahradí prípadnú hlavičku Authorization aktuálnym Bearer tokenom. Provider kontroluje najprv token v pamäti a potom cache; pri chýbajúcom alebo čoskoro expirujúcom tokene použije SAPI client-credentials endpoint.
    Ak je nakonfigurovaný refresh lock, po získaní zámku znovu načíta cache. Samotné tokenové volanie používa obyčajný transport bez Bearer dekorátora. Bežné Integrator volania prechádzajú cez IntegratorTokenRequestSender, ktorý odstráni Authorization a nastaví X-Integrator-Token.
    PDS endpoint používa samostatný ApiConnector cez PdsAuthenticatedRequestSender, ktorý vyžaduje jeden neprázdny X-PDS-Secret a odstráni Authorization aj X-Integrator-Token. Oba Integrator sendery delegujú do toho istého ProviderTransport; všetky vetvy odovzdajú request executor stacku.
    Vstavané cURL executory pri vykonaní použijú interný Transport\Execution\ProviderRequestUrlResolver, ktorý spojí base URL s relatívnou cestou a overí výslednú HTTPS adresu. Iba SAPI/Gateway 401 spustí zahodenie SAPI tokenu a jeden pokus s obnoveným tokenom; táto obnova je oddelená od HTTP retry politiky.
  5. Kontroly a pokusy o prenos. Predvolený executor je zvonka dovnútra zložený ako (voliteľný) RejectionObservingHttpRequestExecutor → CircuitBreakerHttpRequestExecutor → RetryingHttpRequestExecutor → BackpressureHttpRequestExecutor → RateLimitRecordingHttpRequestExecutor → voliteľný logger → voliteľné metriky → cURL executor.
    Circuit breaker môže volanie zablokovať pri otvorenom okruhu. Backpressure pred každým pokusom skontroluje cooldown pre daný request a pri aktívnom limite vyhodí RequestDeferredException ešte pred sieťou; zámok drží iba počas pokusu, nie počas čakania pred ďalším pokusom.
    Retry opakuje iba request označený ako bezpečný: pri chybe spojenia alebo pri odpovedi 429/5xx, ak to povoľuje retry politika a odpoveď poskytovateľa označuje ako opakovateľnú. Pri 429 sa uloží cooldown podľa Retry-After, alebo podľa nakonfigurovanej náhradnej hodnoty, ak hlavička chýba.
    Pri opakovaní určuje čakanie platná hlavička Retry-After alebo backoff politika. Ak sú nakonfigurované, logger a metriky zaznamenajú každý reálny pokus.
  6. cURL prenos. Executor odošle metódu, URL, hlavičky a telo. Pridá Content-Type: application/json, ak request má telo, a príslušnú Accept hlavičku. Používa iba HTTPS, overuje TLS certifikát aj názov hostiteľa a nenasleduje presmerovania.
    Odpoveď číta do konfigurovateľného limitu; po jeho prekročení prenos preruší a vyhodí ProviderResponseTooLargeException, ktorá sa automaticky neopakuje. Inak vráti surový status, telo a vybrané hlavičky (Content-Type, Retry-After a identifikátory korelácie/požiadavky) v HttpExchangeResult. cURL vrstva JSON ani XML neinterpretuje.
  7. Spracovanie odpovede. ApiConnector akceptuje iba HTTP status 2xx. Ostatné statusy prevedie na ProviderErrorResponseException so statusom, hlavičkami a telom odpovede. Pri JSON odpovedi dekóduje objekt alebo zoznam a statická factory endpointu (<Resource>Factory alebo <Resource>Mapper) vytvorí Core model; úspešné 204 bez tela sa mapperu odovzdá ako prázdne pole.
    Neplatný JSON/XML alebo neplatná štruktúra odpovede skončí ako InvalidProviderResponseException s HTTP kontextom. XML sa pred vrátením bezpečne parsuje. Pri send() sa telo úspešnej odpovede nespracúva, keď ho operácia nepotrebuje. Endpoint vráti Core model (alebo bool/void), ktorý adaptér odovzdá hostiteľovi; samostatné response DTO ostáva iba pre OAuth SapiTokenResponse.

Konkrétne retry limity, cooldowny, zdieľanie stavu a nastavenie executorov opisuje HTTP transport a autentifikácia; typy chýb a správanie pri neistom výsledku sú v chybách, retry a idempotencii.

Odoslanie dokladu¶[upraviť zdroj]

Hostiteľ môže vytvoriť XML alebo ho dostať z iného systému a naplniť OutboundDocumentPayload. Ak už pracuje s UblDocumentDraft, môže namiesto ručného skladania payloadu použiť Core kontrakt UblDraftSubmissionInterface, ktorý implementuje UblDraftSubmission.

Obe cesty končia pri rovnakom payload modeli a gatewayi. Konektor poskytuje samostatné lokálne a vzdialené kontroly, ale odosielací adaptér ich sám nespúšťa.

flowchart LR
    Draft[UblDocumentDraft] -->|pri priamom odoslaní| SubmissionService[UblDraftSubmission]
    SubmissionService --> Writer[UblDocumentWriter]
    Writer --> XML[UBL XML]
    XML --> Payload[OutboundDocumentPayload]
    Source[XML z iného systému] --> Payload
    Payload --> Local[Voliteľné lokálne čítanie a validácia]
    Payload --> Discovery[Voliteľný Peppol Discovery]
    Payload --> RemoteCheck[Voliteľná Gateway validácia]
    Payload --> Send[DocumentSubmissionGatewayInterface]
    Send --> Request[SendDocumentRequest]
    Request --> Endpoint[SendDocumentEndpoint]
    Endpoint --> Body[DocumentSubmissionRequestMapper]
    Body --> SAPI[POST /sapi/document/send]
    SAPI --> Result[DocumentSubmissionResult]

Príjem dokladu¶[upraviť zdroj]

Príjem pozostáva z troch oddelených volaní. Zoznam obsahuje metadáta a kurzor ďalšej stránky; detail stiahne telo dokumentu; operácia acknowledge samostatne vykoná technické potvrdenie príjmu.

    Ubl --> Process
    Process --> Ack[POST acknowledge]

SapiReceivedDocumentProvider implementuje ReceivedDocumentProviderInterface a skladá endpointy pre list, detail a acknowledge. ReceivedDocumentMetadataFactory validuje povinné polia a vytvára Domain\EFaktura\ReceivedDocumentMetadata.

ReceivedDocumentPage nesie položky stránky spolu s nextPageToken; ReceivedDocumentPayload obsahuje metadáta detailu cez metadata(), payload cez xml() a formát oznámený poskytovateľom cez payloadFormat().

acknowledge() vracia ReceivedDocumentAcknowledgement s ID dokladu, stavom a časom potvrdenia z odpovede SAPI.

SapiReceivedDocumentProvider::getInboxPage() prijíma ListReceivedDocumentsRequest s participantom a voliteľnými hodnotami PageToken, PageSize a status filtrom RECEIVED alebo ACKNOWLEDGED. Endpoint mapuje request na hlavičku a query.

Pri ukladaní kurzora použite PageToken::value() a pri obnove PageToken::fromString(); veľkosť vytvorte cez PageSize::fromInt(). OpenAPI má query limit ako voliteľnú s predvolenou hodnotou 20.

ReceivedDocumentPayloadFactory overí metadáta, payload a to, že payloadFormat je prítomný reťazec (schéma SapiReceivedDocumentDetailResponse); OpenAPI preň neurčuje enum.

Adaptér prenesie metadáta vrátane creationDateTime a hodnotu formátu do Core modelov bez normalizácie; providerové ID v ReceivedDocumentMetadata a ReceivedDocumentReference majú typ ProviderDocumentId.

ReceivedDocumentPayload poskytuje XML cez xml(); ak ho hostiteľ chce čítať ako UBL, samostatne zavolá $ublReader->read($payload->xml()). Čítanie nespúšťa obchodnú validáciu ani acknowledge; obe operácie hostiteľ riadi samostatne.

DocumentRequestContext zostáva samostatnou hostiteľskou logovacou hodnotou; neposiela sa poskytovateľovi a rovnakú referenciu možno použiť na stiahnutie aj potvrdenie.

Poznámka

Konektor neurčuje, kedy hostiteľ uloží obsah alebo zavolá acknowledge.

UBL modely a lokálne validácie¶[upraviť zdroj]

Načítanie XML, zápis draftu a validácia sú lokálne operácie. Nespúšťajú API volanie.

flowchart LR
    Draft[UblDocumentDraft + UblDraft*] --> Writer[UblDocumentWriter]
    Writer --> XML[UBL Invoice alebo CreditNote XML]
    XML --> Loader[UblXmlDocumentLoader]
    Loader --> XmlDoc[UblXmlDocument]
    XmlDoc --> Reader[UblDocumentReader]
    Reader --> Model[UblDocument: header + content]
    XmlDoc --> XSD[UblSchemaValidator]
    XmlDoc --> Schematron[PeppolSchematronValidator]
    XSD --> XsdStage[UblSchemaValidationStage]
    Schematron --> PeppolStage[PeppolSchematronValidationStage]
    XsdStage --> Pipeline[UblValidationPipeline]
    PeppolStage --> Pipeline
    Pipeline --> Combined[LocalUblValidator]
    Combined --> Result[LocalUblValidationResult]
SmerTriedyVýsledné údaje
Draft → XMLUblDocumentDraft, UblDraftParty, UblDraftLine, UblDraftTaxCategory, UblDraftTaxSubtotal, UblDraftTotals, UblDraftPaymentMeans, UblDocumentWriterUBL 2.1 Invoice alebo CreditNote XML. Desatinné sumy a množstvá sa prenášajú ako presné reťazce.

Doplnkové pravidloPeppolBillingHeaderRules, PeppolBillingHeaderValidationStageKontrola BR-CO-25 pre kladné faktúry bez dátumu splatnosti a platobných podmienok; pribalený Schematron toto pravidlo neobsahuje.

Vráti LocalUblValidationResult s nálezmi a metadátami každého kroku: trvanie, stav a dostupné verzie pravidiel.

Lokálne kontroly nepodmieňujú čítanie ani zápis UBL a samy nevolajú Gateway. Verzie, licencie, presné cesty súborov a aktualizačný postup sú v lokálnych validačných podkladoch. Súhrn štandardov je v technickom prehľade eFaktúry.
